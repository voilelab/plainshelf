# 10 — 模型調度守則

適用對象：主對話（指揮官）。目的：主 context 只留判斷與結論，原始資料留在 subagent 裡。
依據：`00-diagnosis.md` 問題 2（主對話下場導致失焦）與問題 3（模型名憑印象亂寫）。

---

## 1. 指揮官不下場

主對話**只做**：理解需求、拆解任務、派工、整合結論、做最終決定、對使用者溝通。
以下工作**一律派 subagent**，主對話不自己做：

| 工作型態 | 派給 | 判準 |
|---|---|---|
| 位置未知的搜尋（「X 在哪實作」「哪些地方呼叫 Y」） | `Explore` | 只要**不確定**第一次就能找到，就派 |
| 超過 3 個檔案的閱讀理解 | `Explore` | 3 檔以內且位置已知 → 自己讀 |
| 網頁研究、文件查證 | `general-purpose` | 一律派，搜尋結果很佔 context |
| 批次改檔（>5 檔的機械性修改） | `general-purpose` | 同一 pattern 重複套用就算機械性 |
| 長 log / 測試輸出分析（>200 行） | `general-purpose` | 先落檔，把檔案路徑給 agent |
| 實作一個獨立子功能 | `general-purpose` | 能寫出明確驗收條件就能派 |

**例外（自己做，不派）**：已知確切位置的單點讀取和編輯、跑一條指令看結果、3 行以內的修改。為小事開 agent 是浪費 —— agent 冷啟動要重新建立 context。

## 2. 派工三件套（缺一不派）

每個派工 prompt 必含（可填空模板見 `30-prompt-templates.md`）：

1. **目標與動機** — 不只說做什麼，要說為什麼。動機讓 agent 在遇到模糊處時能做正確取捨。
   - 壞：「把 handleImport 的錯誤處理改好」
   - 好：「handleImport 在來源檔編碼偵測失敗時回 500，使用者看不出原因。改成回 400 並帶可讀錯誤訊息，因為這是使用者操作錯誤不是伺服器錯誤」
2. **驗收條件** — 可逐條打勾的清單，不是形容詞。「品質要好」不是驗收條件；「`go test ./server/...` 通過且新增至少一個失敗案例的測試」是。
3. **回報格式** — 明確說要回什麼（見第 4 節回報合約），否則 agent 會把整個過程倒回來。

另外必附：相關檔案路徑（省 agent 的搜尋時間）、範圍邊界（「不要動 X」「不要順手重構」）。

## 3. Model 與 effort（照實，不憑印象）

Agent tool 的 `model` 參數**只接受四個值**：`haiku`、`sonnet`、`opus`、`fable`。
（`fable` 是否可用取決於當下方案；不可用時 `opus` 就是最高階。）

| 任務 | model |
|---|---|
| 機械性批次修改、格式轉換、簡單搜尋 | `haiku` |
| 一般搜尋、實作、重構、審查、研究（**預設值**） | `sonnet` |
| 跨模組設計、疑難除錯、第二意見、對抗審查 | `opus` |

**effort 事實**：Agent tool **沒有** effort 參數。要固定 reasoning effort，唯一辦法是在 `.claude/agents/<name>.md` 建自訂 agent 定義，在 frontmatter 指定 model 與 effort。日常派工不需要這麼做；只有反覆出現的固定角色（例如驗收員）才值得建定義檔。

## 4. 回報合約（寫進每個派工 prompt 的「回報格式」欄）

- 結論先行，全文 ≤ 400 字。
- 位置一律用 `檔案路徑:行號`，不貼大段程式碼（單段引用 ≤ 10 行）。
- 長產物（報告、大 diff 說明、蒐集的資料）寫成檔案，回傳路徑。臨時檔放 scratchpad，要保留的放 repo。
- 明確區分「驗證過的事實」與「推測」，推測要標註。
- 失敗要照實報：做了什麼、跑了什麼指令、確切錯誤輸出。不准回「大致完成但有些小問題」這種模糊話。

## 5. 升降級路徑

- `haiku` 失敗 **1 次** → 直接升 `sonnet` 重派，不給 haiku 第二次機會（重試成本高於升級成本）。
- `sonnet` 在**同一個子任務**失敗 **2 次** → 升 `opus`，且 prompt 必須帶完整失敗軌跡（兩次分別做了什麼、指令、確切錯誤輸出），否則 opus 只是重走一遍。
- `opus` 也解不掉 → 停，把失敗軌跡整理給使用者（見 `20-judgment.md` 第 3 節）。
- **降級**：高階模型解出可複製的模式後（例如修好第一個案例），把模式寫成明確步驟，降回 `haiku`/`sonnet` 批次套用到其餘案例。
- **同一件事最多重試兩輪**（含升級在內）。兩輪後還不行，問題不在模型等級，在方法或需求理解 —— 換路或問人。
- 續用同一個 agent 用 `SendMessage`（保留它的 context，適合追問）；升級或換方法時**開新 agent**（舊 context 裡的錯誤方向會污染）。

## 6. 驗證不自驗

做事的 agent 不能自己宣告合格。驗收一律派 **fresh-context** 的新 agent（不知道實作過程，只拿驗收條件）：

| 產出類型 | 驗法 |
|---|---|
| 檔案/文件 | read-back：新 agent 讀檔，對驗收條件逐條核對，回報每條 pass/fail |
| 程式碼 | 實跑：用 CLAUDE.md 對照表的指令跑 build + test，貼結果。測試沒跑 = 沒驗 |
| 高風險判斷（安全、資料遷移、刪除、對外行為） | 第二意見：派 `opus` 獨立評估；或讓兩個 agent 各給一版答案，比較後擇優 |

驗收 agent 的 prompt 只給：驗收條件 + 產出位置 + 回報格式。**不給實作過程的敘述**，避免被實作者的說法帶著走。
