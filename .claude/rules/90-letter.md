## 三件使用者沒問、但我認為對這個環境最重要的事

### 1. 這個 repo 的開發節奏是「小 PR 進 dev」，你的產出要配合這個節奏

git 歷史顯示：幾乎所有變更都是 `claude/*` 分支 → 小 PR → merge 進 `dev`，一個 PR 一件事，docs 改動也單獨成 PR。這意味著：不要在一個分支上堆多個不相干的改動；diff 保持在「一個 PR 能被人審完」的尺寸；改動大就主動拆。使用者顯然親自審每個 PR —— 你的 diff 是寫給他看的，不是寫給 CI 看的。另外 CHANGELOG.md 有專用 skill（`update-changelog`），使用者在意它的格式，別手寫。

### 2. filesystem-first 是這個專案的靈魂，不是實作細節

`books/` 下的檔案是 source of truth，人類可讀、備份工具友善、Git 友善 —— 這是 README 明寫的產品承諾。所以：任何「把資料搬進資料庫」「加二進位快取格式」「讓 runtime state 變成必需品」方向的建議都違背專案哲學，哪怕技術上更快。改 `shelf/` 裡的資料佈局邏輯時，向後相容性（既有使用者的 vault 還能不能開）是第一考量，這類改動一律先問使用者。Non-goals 清單（EPUB、雲同步、多使用者…）是使用者深思後的決定，不要「好心」建議加回來。

### 3. 使用者的工作語言是繁體中文，且他讀得很仔細

對話用繁體中文回覆；commit message 和程式碼註解維持英文（跟 repo 現狀一致）。他給的指示通常結構清楚、有明確驗收標準 —— 這代表他也會用同樣標準檢查你的產出。「宣稱做了」和「做了」的差距他看得出來，誠實回報 blocked 或失敗永遠比含糊的「大致完成」好。

## 這套制度最可能的退化方式，與預防法

1. **規則與現實漂移**：工具鏈更新（just 裝進容器了、模型名單變了、repo 結構改了）但沒人改對照表，之後的 session 發現規則是錯的，進而**整套不信**。這是最致命的退化 —— 一條錯規則的代價是全部規則的公信力。預防：發現漂移照 `40-maintenance.md` 第 5 節立即修正並記錄，事實類修正不用等使用者。
2. **lessons 變垃圾場**：什麼都往 `50-lessons.md` 塞，30 條門檻到了也沒人精簡，最後開工掃一遍變成沒人做的具文。預防：寫入前先過「會不會替下個 session 省 10 分鐘」的判準；到門檻就照 `40-maintenance.md` 第 4 節觸發精簡。
3. **貨物崇拜派工**：照抄 `30-prompt-templates.md` 但動機欄填一句廢話、驗收條件抄成「程式碼正確運作」。模板的形式都在，判斷的內容全空 —— 這比不用模板更糟，因為看起來合規。預防：模板裡標「必填」的欄位填不出具體內容，代表你還不理解任務，先回去理解，不要派工。
4. **CLAUDE.md 重新膨脹**：每個人都覺得自己那條很重要，往 CLAUDE.md 塞，兩個月後又是每 session 常駐幾千 token 的大雜燴。預防：80 行硬上限（`40-maintenance.md` 第 4 節），新內容進 rules/ 子檔，CLAUDE.md 只加一行路由。

## 誠實條款（這套制度做不到的事）

拆解、驗證、fresh-context 驗收、多答案評審 —— 這些補得了**執行品質**，你照著做就能接近高階模型的產出下限。但兩類問題補不了：

- **模糊題**（需求本身不清楚）：任何模型都不該硬猜。處理法在 `20-judgment.md` 第 3 節：先查 repo 內有沒有前例，沒有就給選項問使用者。
- **品味判斷**（UI 取捨、文案語氣、API 設計美感、產品方向）：checklist 驗不出品味。處理順序：升級到 `opus` 拿第二意見 → 還是拿不準就給使用者 2–3 個具體選項（附各自後果）→ 使用者不在就選最保守可回退的，並明確標註「此為品味判斷，可改」。**明說做不到，好過假裝做得到。**
