# 30 — 派工 prompt 模板

用法：複製對應模板，填入 `{...}` 空格，作為 Agent tool 的 `prompt`。
`{...}` 全部要填；寫著「必填」的欄位空著就不要派工。
model 選擇依據 `10-delegation.md` 第 3 節；模板上標的是預設值。

---

## T1 搜尋 / 定位（subagent_type: `Explore`，model: `sonnet`；簡單關鍵字定位可用 `haiku`）

```
在 plainshelf repo 裡回答：{要找什麼，一句話}。
背景：{為什麼要找，主任務是什麼}（必填 — 讓你判斷哪些結果相關）。
搜尋廣度：{medium | very thorough}。
已知線索：{相關關鍵字 / 可能的目錄，沒有就寫「無」}。

回報格式：
- 每個發現一行：`檔案路徑:行號` + 一句話說明它是什麼。
- 最後一段：對「{要找什麼}」的直接回答（≤5 句）。
- 找不到也是有效答案：列出你搜過的 pattern 與目錄，說「未找到」，不要硬湊。
```

## T2 實作（subagent_type: `general-purpose`，model: `sonnet`）

```
任務：{做什麼，一句話}。
動機：{為什麼要做、解決誰的什麼問題}（必填）。
相關檔案：{已知的檔案路徑清單}。
範圍邊界：不要動 {不可碰的檔案/區域}；不要順手重構無關程式碼。
先讀 CLAUDE.md 的指令對照表與陷阱（repo 根目錄），照裡面的指令跑測試。

驗收條件（逐條可打勾，必填）：
1. {例：`go test ./server/...` 全數通過}
2. {例：新增測試覆蓋 {行為}，且該測試在未修改的程式碼上會 fail}
3. {例：`git diff --stat` 只含 {預期檔案}}

回報格式：結論 ≤400 字；改動清單（`檔案:行號` + 一句話）；測試指令與輸出結尾；
未達成的驗收條件照實列出，不要含糊帶過。
```

## T3 重構（subagent_type: `general-purpose`，model: `sonnet`；跨模組的結構調整先派 `Plan` 出計畫）

```
重構目標：{把什麼從什麼樣改成什麼樣}。
動機：{現狀造成什麼問題}（必填）。
不變式（必填 — 重構的定義就是行為不變）：
- 對外行為完全不變：{列出可觀察行為，例：API 回應、檔案格式}
- `server/api_contract_test.go` 不得修改。
步驟約束：小步進行，每完成一個內聚步驟跑一次 `go test ./...`，紅了先修再繼續。

驗收條件：
1. 全部測試通過（改前先跑一次確認基線是綠的，貼兩次輸出）。
2. {重構目標的可檢查描述，例：X 不再 import Y}
3. 測試檔的 diff 只有 {預期，通常是「無」}。

回報格式：結論 ≤400 字；每個步驟一行；基線與最終測試輸出。
```

## T4 研究 / 查證（subagent_type: `general-purpose`，model: `sonnet`；需要權衡結論的用 `opus`）

```
問題：{要回答什麼}（必填，寫成可被回答的問題，不要寫成主題）。
用途：{答案會拿來做什麼決定}（必填 — 決定研究深度）。
來源優先序：repo 內（docs/、程式碼、git log）→ 官方文件 → 其他網頁。
時效敏感的資訊（版本號、API、價格）必須查證，不可用訓練記憶回答。

回報格式：
- 直接回答 ≤300 字，區分「查證過的事實（附來源 URL 或 檔案:行號）」與「推測（標註）」。
- 查不到就寫查不到 + 你查過哪裡。禁止編造。
- 長篇整理落檔到 scratchpad，回傳路徑。
```

## T5 審查 / 驗收（subagent_type: `general-purpose`，model: `sonnet`；高風險改動用 `opus`）

⚠ 必須是 fresh-context 的新 agent。prompt 裡**不要**描述實作過程或「我認為已經完成」——只給條件與位置。

```
你是驗收者，之前的實作過程你不知道，也不需要知道。獨立核對以下產出：
產出位置：{檔案路徑清單 / branch 名 / diff 範圍（如 `git diff dev...HEAD`）}。

逐條核對驗收條件（必填，照抄派工時的原始條件，不要轉述）：
1. {條件一}
2. {條件二}
程式碼類：親自跑 CLAUDE.md 對照表裡的對應測試指令，以實際輸出為準，不採信任何聲稱。
文件類：完整讀過檔案再判定，不要只看開頭。

回報格式：每條 pass/fail + 證據（測試輸出片段或 檔案:行號）；
另列「條件之外注意到的問題」（有就列，沒有寫無）；最後一行總判定：通過 / 不通過。
```

---

## 通用附註

- 每個模板都可以加一行「若遇到 {預期外狀況} 就停止並回報，不要自行擴大範圍」。
- 派工後 agent 回報若不符合你要求的回報格式，用 `SendMessage` 要求補齊，不要自己下場重做。
- 兩次派工失敗的處理見 `10-delegation.md` 第 5 節，不要無限重派。
