# 20 — 判斷力 rubric

適用對象：主對話。每條判準附正例（該這樣）與反例（別這樣）。
這份檔案回答五個問題：何時升級、何時算完成、何時問人、何時換路、品質底線怎麼驗。

---

## 1. 何時該升級模型（配合 `10-delegation.md` 第 5 節）

**判準**：任務需要「跨多個模組同時推理」「在互相衝突的需求間取捨」「從稀少線索反推根因」其中之一，就從 `opus` 起跳；純執行類一律從 `sonnet` 起跳。

- ✅ 正例：測試在 CI 過、本地不過，且錯誤訊息指向不相干的檔案 —— 根因反推題，直接派 `opus`。
- ❌ 反例：把 20 個檔案裡的舊 API 呼叫換成新 API —— 模式明確的批次工作，派 `opus` 是浪費，`sonnet` 做第一個、`haiku` 批次套用其餘。

## 2. 何時算真的完成

**判準**：三項全滿足才能對使用者說「完成」——
(a) 當初的驗收條件逐條打勾；(b) 有驗證證據（測試輸出、read-back 結果），不是「應該沒問題」；(c) 沒有留下未聲明的副作用（`git status` 乾淨、沒有偷改無關檔案）。

- ✅ 正例：「三個驗收條件都過：`go test ./server/...` 全綠（輸出如下）、新增的失敗案例測試會在修改前的程式碼上 fail（有實際回退驗證）、api_contract_test.go 未動。」
- ❌ 反例：「我已經修改了 handleImport 的錯誤處理，邏輯上應該正確。」—— 沒有跑測試就是沒完成，這句話不准出現。
- 特別條款：**改了程式碼但測試跑不動**（環境問題等）→ 不是完成，是 blocked，照實回報 blocked 的原因。

## 3. 何時該停下來問使用者

**判準**：滿足任一條就停下用 AskUserQuestion 問，不要猜——
(a) 破壞性且難回復（刪資料、force push、改 `books/` 資料格式）；
(b) 對外可見（開 PR 以外的 GitHub 操作、發 comment、動 Linear）且使用者沒明說；
(c) 需求存在兩種合理解讀，且**選錯的返工成本 > 問一次的成本**；
(d) 誠實條款情境：品味題（UI 取捨、文案語氣、產品方向）—— 弱模型在這類題目上的自信與正確率無關，給 2–3 個選項讓使用者選，不要假裝有答案。

- ✅ 正例：「移除舊的 import 流程」可以指刪程式碼或只藏入口，兩者 diff 完全不同 —— 問。
- ❌ 反例：「要用哪種錯誤訊息格式」而 codebase 裡已有一致慣例 —— 自己查 `server/` 現有 handler 照做，這是可查證的事實不是品味題。
- 注意：**能自己查證的事實不要拿去問**。問之前先確認 repo 裡真的沒有答案。

## 4. 方向錯了的訊號（換路，不是再試一次）

**判準**：出現任一訊號，立即停手 → 回滾到最近的乾淨狀態（`git checkout` / `git stash`）→ 重讀原始需求 → 換方法或升級或問人：

1. **同一個錯誤第三次出現**（訊息相同或根因相同）—— 你的假設錯了，重試只是加碼。
2. **修 A 壞 B，修 B 又壞 A** —— 兩者共享你沒看見的耦合，先找出耦合點再動手。
3. **diff 大小明顯超過任務應有規模**（例如「修一個 bug」長出 300 行 diff）—— 大概率在錯的層次上解問題。
4. **想改測試來遷就實作** —— 除非有明確證據測試本身錯了（並向使用者聲明），否則這是方向錯誤的確定訊號。
5. **連續第二次說「這次加個 workaround 一定行」** —— workaround 疊 workaround 就是換路訊號。

- ✅ 正例：第三次遇到 `embed dist/*` 編譯錯誤 → 停手查根因 → 發現要先 build frontend → 把教訓寫進 `50-lessons.md`。
- ❌ 反例：測試不過 → 在測試加 skip → 宣告完成。任何情況下都不可以。

## 5. 品質底線怎麼驗（最低集，不可再減）

按產出類型，宣告完成前必跑：

| 改了什麼 | 最低驗證 |
|---|---|
| Go 程式碼 | build frontend（若 dist 不在）→ `go test ./...`；碰 desktop 則加 `cd desktop && go test ./...` |
| 前端程式碼 | `npm --prefix frontend run build`（內含 vue-tsc 型別檢查）；碰 UI 行為則加 e2e |
| server API | 上述 Go 測試 + 確認 `server/api_contract_test.go` 是否需要同步更新（契約變更要先問，見第 3 節 (c)） |
| 文件/規則檔 | fresh-context agent read-back（見 `10-delegation.md` 第 6 節） |
| CHANGELOG | 用 `update-changelog` skill，不要手寫 |

**harness 的極限（誠實條款）**：以上機制補得了執行品質（拆解、驗證、多樣本評審都做得到），補不了模糊題與品味判斷。遇到後者的處理順序：(1) 在 repo / docs / 歷史 PR 裡找使用者過去的選擇當依據；(2) 找不到就給選項問使用者；(3) 使用者不在且非做不可 → 選最保守可回退的一項，並在回報裡明確標註「此處是品味判斷，我選了 X，理由 Y，可改」。不要編造確定性。
